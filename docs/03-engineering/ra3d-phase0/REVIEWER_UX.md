# 审核工作台交互规格 P0.1

**DESIGN_ONLY / 静态概念 / 无实际审批。** 目标是让有任务授权的真人快速核对有限报告，
理解自己签署的内容与仍然未知的部分。品牌为 VEYFRONT；操作员和 Reviewer 使用内部工作台。
不建设 CRM、客户入口或完整 SPA。可参考 [静态桌面/手机概念图](mock/reviewer-workbench.html)。

## 1. 信息架构与角色视图

顶部固定：工作区/租户可读名、当前真人及活动角色、报告 id/vN、捕获日期、当前版本状态、
“仅内部，尚未分享”。敏感完整租户标识仅有权限者可查看，不允许通过输入 id 切换到他人租户。
角色切换须来自认证授权，不能是浏览器选项改变权限。

| 视图 | 要回答的业务问题 | 主要内容 |
| --- | --- | --- |
| 待审任务列表 | 我负责哪几份、为何阻断？ | 分配给本人、0–3 个真实问题、版本、来源覆盖、等待时间；不显示神秘总分 |
| 版本审核主区 | 原文究竟支持什么？ | 左侧逐问题及事实/假设/行动/复核方法，右侧确切来源；报告全页预览是同一 hash 的精确对象 |
| 版本差异 | 上版之后改了什么？ | 逐字改动、HTML/CSS、证据/位置、Guard/规则模型版本、覆盖/租户/策略变化；新版须整份复审 |
| 决策确认 | 我以谁的身份批准哪一份？ | 操作、版本、完整摘要可展开、逐项处理、理由、限制、身份、明确“不分享” |
| 历史记录 | 哪次真实决定现在仍有效？ | 不可覆盖事件、责任人、服务端时间、目标版本、当前有效性与失效原因；不把旧绿标当当前授权 |
| Owner 授权边界 | 审核后还差什么？ | 审核状态与分享状态分列；“尚无分享授权”。本阶段 Owner grant 入口始终禁用 |

Operator 看见“准备并提交审核 / 按意见生成新版”；Review 按钮不可用并给出权限解释。
Reviewer 看见本人的签署操作；没有 Owner 发放权限。Owner 可按原权限明确审核，但另有独立分享职责；
同一真人持有两种角色也须两次动作。Worker/模型不出现可签署身份。

## 2. 桌面主流程（建议 1280px）

采用安静的深蓝标题、白底正文与清晰分隔；蓝绿只表示字面来源绑定，铜色表示待复核的解释。
颜色必须配文字/图标，不能用绿色暗示认证真实性。问题区约 58%，证据区约 42%，两侧独立定位，
顶部仍能看到正在审核的版本；页面滚动不遮住原文。完整报告预览、diff 和证据三者有清晰切换。

每项显示：

1. 采购任务与观察事实，例如“本次记录的产品页 href `/contact` 的目标返回 HTTP 404”。
2. **原 Guard 状态**：SOURCE_FACT_BINDING_VERIFIED（仅捕获时的字面/响应事实）；
   HUMAN_REVIEW_REQUIRED（假设/建议仍未获事实证明）；REJECTED（阻断，不能批准）。
3. 右侧显示原始 URL、href/定位、捕获时间、HTTP/coverage、精确 quote 与字节区间、native bridge。
   原始 HTML 只以转义文本展示；默认无外链，不导航到源站，不执行原网页。
4. 当前事实的人工处理：“已核对字面事实”；假设：“保留为假设 / 提出修改 / 拒绝该措辞”；
   行动和复核方法：“接受为候选建议 / 提出修改”。接受建议不等于批准执行网站操作。
5. 正向网站自述、覆盖和限制也在复核范围；不能只审一个错误链接，忽略标题/页脚中的认证或销售承诺。

证据查阅动作记录在当前 session 的 target 下，但勾选/打开面板不构成审批，也不证明理解。
批准前必须完成全部展示内容的适当处理，确认覆盖限制且无机器 REJECTED/未绑定内容。

## 3. 明确的决策交互

| 动作 | 自然中文文案 | 前置/确认 | 提交后的可见反馈 |
| --- | --- | --- | --- |
| APPROVE | “批准这个版本（不分享）” | 逐项复核完成、来源有效、版本未变；二次确认精确 vN/摘要和本人身份 | 只有持久成功才显示“已记录审核通过 · 仅内部 · 分享未授权” |
| REQUEST_CHANGES | “退回修改” | 必填具体条目/措辞与 1–2000 字理由；可附替换建议 | “已退回。修改将生成新版本，需要重新审核。” |
| REJECT | “拒绝此版本” | 必填理由；说明本轮关闭，保留证据和历史 | “本版本已拒绝。原记录已保留，不能直接改成通过。” |
| 内部范围确认 | “确认已核对检查范围” | 仅 0 问题且 native=null；确认未知/受限部分 | “范围已核对，仅内部记录；不是 L1 报告批准，不能外发。” |

确认区文案：“我已核对本版本的原始证据及限制；假设与候选建议不作为已证实事实。
本次操作只记录内部审核决定，不授权外发、表单提交、网站修改或报价。”
显示具体已登录的人和任务角色；不能让用户输入一个“审核员姓名”就成为身份。
Hash 默认短显示，可展开完整值；真正提交始终使用完整摘要。

确认前不默认勾选，不靠滚到底部自动批准，不把“保存备注”“生成草稿”变成审核通过。
按钮点击后固定同一个幂等 key，禁用重复点击，显示“正在保存决定”；不得乐观显示成功。
网络超时显示“尚未确认保存结果，正在核对回执”；先查询同 key，不能随机换 key 重新批准。
重新读取发现新版时，旧决定回执显示“历史记录，当前版本已变更”，不能显示有效绿标。

## 4. 修改退回与 diff

Reviewer 的修改框只提出私有 RevisionProposal，不直接编辑证据或批准的 HTML。
现有固定 RA3C 候选只支持限定措辞，**本设计不承诺任意改写已经可保存为有效报告**。
未来版本化编辑输入获 Owner 放行后，由 Operator 生成新草稿并重放所有绑定。
保存修改意见与“提交新版审核”分开，失败保留私有意见且状态不跳转。

diff 显示 v1/v2 摘要、文字前后、来源/Guard/布局/版本变化及原因。即使只是页脚或 CSS 变了，
也显示“这是新版本，旧批准不能沿用”。可以提示相同片段，不能自动复制“已核对”或批准。
旧版始终只读且带“历史版本 / 已失效”，默认打开最新，手动打开历史不得调用客户分享路径。

## 5. 手机与无障碍（建议 375px）

上下排列，事实后紧跟其证据和处理区；明确“原文 / 建议 / 版本差异”标题。
证据锚点可返回原问题，焦点应落到对应标题；无内容仅靠 hover 才可见。
操作条最多两层，避免覆盖原文；批准按钮在必要核对完成后才启用，当前 mock 全部 disabled。
长 URL/hash/中文换行，不横向撑开；原文带方向隔离，危险 bidi/control 在进入展示前拒绝。
完整摘要可折行且不省略真实提交值；触控目标建议至少 44px，键盘有可见焦点，状态文本由屏幕阅读器播报。
批准、退回、拒绝都可键盘到达，无默认 Enter 触发批准；二次确认必须说明动作与版本。

## 6. 需要设计的异常视图

| 情况 | 给当前有权限用户的文案 | 数据/操作 |
| --- | --- | --- |
| 提交时新版出现 | “版本已更新。请打开新版并重新核对。” | 清除旧页面待提交操作，不自动提交到新版 |
| HTML 或 quote hash 不符 | “内容完整性检查未通过，暂不能审核。” | 停止展示不可信全文，只给安全错误及 request id |
| REJECTED claim | “该陈述未通过来源校验，请移除或提交新版本。” | 批准禁用，不提供“忽略并批准” |
| 403/UNKNOWN | “本次访问受限 / 证据不足，不能据此认定网站缺陷。” | 作为范围限制；不能自动添加问题 |
| 0 问题 | “0 项可报告问题。可确认检查范围，不能据此批准对外 L1 报告。” | 隐藏 APPROVE，使用独立确认动作 |
| 身份过期/角色收回 | “审核权限已变化，请重新验证身份。” | 清除当前受限内容并禁用操作；意见仅保留在仍获准的服务端私有记录，不写原文到 localStorage/离线缓存 |
| 跨租户/未分配 | “无权访问该审核内容。” | 不显示标题、主体、hash、quote、版本是否存在 |
| 持久化/审计失败 | “决定尚未确认记录成功，请按请求编号核对。” | 没有批准徽章、没有分享入口，恢复不造事件 |
| 分享过期/撤销/新版 | “该授权当前不可使用。” | 不回退旧版本或 cached HTML；无 recipient 私密细节 |

## 7. 原型的实际含义

本包 mock 是单个无脚本的静态 HTML：三个场景、所有控件 disabled、没有表单、可执行审批、
分享、登录或外部资源。没有伪造“真实 Reviewer 已批准”的 UI 状态。
可以展示未来预期态的文字说明，但必须显著标注“设计预期，未执行”。
本阶段视觉审阅仅验证设计表达与布局；不能替代未来受保护身份 + API + DB 的浏览器端到端验收。
