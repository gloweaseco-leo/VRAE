## 一、业务架构（Business Architecture）

### 产品定位与商业对象

- **VRAE（VEYFRONT Rebuild Audit Engine）**：独立、证据驱动的 B2B 企业网站采购商体验诊断引擎，将合法、受控观察的旧网站信息，转化为可复核的诊断发现、可审核的改进建议及可授权交接的商业材料。
- **首个商业使用者：VEYFRONT**。VRAE 不是 VEYFRONT 官网、L2M 自动建站器、Vey2GE 多租户增长经营平台或通用网站漏洞扫描器。
- **第一目标客户**：具有真实出口业务、已有英文网站的中国 B2B 制造/工业企业。首批候选行业为机械设备与工业零部件；广东优先，便于实地销售验证。
- **采购商体验的五项任务**：DISCOVER（能否找到产品）、UNDERSTAND（能否理解技术与应用）、TRUST（能否核实主体及业务事实）、INQUIRE（能否从产品进入咨询）、SEARCH & TECHNICAL（是否具备被搜索发现的基础条件）。

### 产品层级

| 层级 | 受众 | V1.1 定义的交付与权限边界 |
| --- | --- | --- |
| L0 Scout | VEYFRONT 内部销售 | 公开证据、企业适配、候选问题；规则优先、无模型；只内部使用 |
| L1 Initial Audit | 获准接收报告的潜在客户 | 一页、至多三个真实可信问题及证据和建议；人工批准、定向授权分享 |
| L2 Deep Audit | 确认兴趣且获网站属主授权的客户 | 深度采购商旅程、产品结构与改造蓝图；单独授权和商务范围 |
| L3 Sales | 已进入采购讨论的客户 | VEYFRONT 正式方案、报价、验收和交付责任；VRAE 不自动报价 |

### 业务链与权威归属

精准企业发现 / 专业信任内容 / 伙伴推荐 / SEO-GEO → VEYFRONT 诊断入口或内部筛选 → VRAE 安全采集与证据化评估 → 人工审核的一页 L1 诊断 → 客户主动沟通和需求确认 → VEYFRONT Rebuild 方案及合同 → L2M 或人工受控交付 → 经授权的案例、内容和推荐。

- 北极星：**经责任人确认的 E3 合格商机及其完全获客成本**（包含人工、模型与运行费用）；诊断、点击、扫码或报告分享本身不能算 E2/E3。
- VEYFRONT 负责客户关系、同意、报价、交付承诺；VRAE 负责证据、规则、报告和审核；Vey2GE 后续负责增长经营；L2M 负责获授权的重建交付。
- 明确非目标：任意第三方网站自动重建/发布、自动陌生客户外发、无限制采集、伪造 Google 排名/流失额/转化结果、一次性建设通用 CRM/SaaS/多 Agent 平台。

## 二、技术架构（Technical Architecture）

### 已认可的方向和模块

- 独立 VRAE 仓库；**Python 模块化单体**；API 与隔离 Worker 分进程/容器、分凭据和网络规则；独立数据及权限；对外通过 API/事件集成。
- 模块职责：
  - **API**：身份、SourcePolicy、配额、任务创建、查询、审核、报告、分享授权。
  - **Operator Console**：任务池、证据对比、报告审核、审批、成本查询。
  - **Orchestrator**：状态机、持久队列、租约、去重、失败/重试/取消。
  - **Worker**：有界 HTTP Fetch、DOM/浏览器观察、证据提取、规则、可选模型调用。
  - **Rules & Domain**：版本化规则、事实与假设区分、行业包。
  - **Report Service**：报告汇总、审核、受控分享与审计。
  - **Integration Adapters**：VEYFRONT API、Vey2GE 事件、L2M RebuildBrief。

### 分层与运行关系

- **Interface**：REST API、Operator UI、事件消费者及 VEYFRONT Adapter。
- **Application**：SubmitAudit、RunAudit、ApproveReport、IssueShareGrant、SalesHandoff 等用例和状态流转。
- **Domain**：Site、Policy、Audit、Observation、Finding、Report、Review 等约束。
- **Infrastructure**：PostgreSQL repository、对象存储、事务 Outbox、模型提供方、HTTP/Playwright。
- **IndustryPack**：行业适用规则、术语与证据需求；不写死特定行业字段。
- 文档规定的依赖方向：**Interfaces → Application → Domain**；Infrastructure 实现其所需 Port。

同步/异步主链：提交受控申请 → API 在 Policy/配额/幂等检查后持久化并返回 202 → Worker 领取租约 → Safe Fetch / Evidence / Rules / AI 候选 → 持久化结果与错误/费用/审计事件 → Reviewer 审核指定版本 → VEYFRONT 仅读取获批准的报告。

### 技术候选和环境

| 层面 | V1.1 原文 |
| --- | --- |
| 语言和服务形态 | Python 模块化单体；FastAPI/Pydantic 是候选而非定案 |
| 浏览器观察 | HTTP + Playwright 受控只读采集 |
| 数据和队列 | PostgreSQL；事务领取/租约，或待选 pgmq；厂商/区域未最终选定 |
| 计算 | 受限容器或专用 VM，实际平台待选 |
| 模型 | Qwen 或其他经授权的模型候选；供应商、价格、数据地区待确认 |
| 初始环境 | Docker Compose/合成样本、单 Worker、无公网入口 |
| 内部试点 | 受保护的 API、受限 Worker、持久队列/存储；建议并发 1 |
| 公网自助 | 后续另行评估和批准，非默认开放 |

V1.1 同时写明 URL/SSRF、DNS-IP 绑定、robots/授权、只读 HTTP、Worker 网络/凭据隔离、私有存储、限额、幂等和恢复等约束。

## 三、数据架构（Data Architecture）

### 数据主权

| 数据资产 | V1.1 的权威来源 |
| --- | --- |
| 企业候选及公开站点观察 | VRAE 观察对象，不代表工商法定身份 |
| SourcePolicy 与授权证据 | VRAE |
| PageSnapshot、Evidence、RuleExecution | VRAE |
| Finding、Hypothesis、ReportVersion | VRAE |
| 真实联系人、企业微信及咨询收据 | VEYFRONT |
| 经确认 E2/E3 与商机状态 | VEYFRONT 或后续指定的 Vey2GE 经营权威 |
| Rebuild 项目与交付成果 | L2M / 人工交付主体 |

### 存储与逻辑数据链

- **PostgreSQL**：身份/权限、事务业务对象、状态、审批、版本、费用、Outbox 和队列游标。
- **私有对象存储**：获准保留的 HTML、DOM 摘要、截图和报告。
- **持久队列**：PostgreSQL 事务领取和租约，或待选 pgmq；需要重试、死信及恢复。
- **运营日志/指标**：非 PII 的 job_id、规则版本、状态、费用、错误码等。

逻辑主链：Tenant / AccountCandidate / Site / SourcePolicy → AuditRequest → AuditRun → PageSnapshot → EvidenceItem → RuleExecution → Finding → ReportVersion → ReviewDecision / ShareGrant；AuditRun 还关联 UsageRecord；Tenant 关联 OutboxEvent；AuditRequest 关联 IntegrationLink。Evidence 与 Finding 是多对多证据引用关系。

### V1.1 的候选物理表（非已落地事实）

| 数据域 | 表名候选 |
| --- | --- |
| 身份 | tenants、members、role_grants |
| 企业与网站 | account_candidates、sites |
| 授权 | source_policies |
| 请求与执行 | audit_requests、audit_runs、queue_jobs / leases |
| 快照与证据 | page_snapshots、evidence_items |
| 规则与发现 | rule_executions、findings、finding_evidence |
| 报告与审核 | reports、report_versions、review_decisions |
| 授权分享 | share_grants |
| 对接与事件 | integration_links、outbox_events |
| 费用 | usage_records |

### 数据约束与生命周期

- 事实要能追溯到许可、URL/页面版本、观察时刻、证据 SHA 和规则版本；原始观察不静默覆盖，修订生成新的决定或报告版本。
- 用 tenant_id/workspace 隔离；诊断申请≠真实询盘；报告分享≠阅读或成交；站点域名≠企业法人唯一标识。
- 数据生命周期：**Create → Capture → Evaluate → Review → Share → Retain/Delete**。
- 外部分享绑定获批准的 report_version，设置期限和撤销；对外数据最小化。
- **候选**原始 HTML/截图保留约 30 天，授权报告约 90 天；原文注明并非已生效政策或法律结论。
- 业务写入依单事务和幂等约束；Outbox 与本地状态变更同事务。

## 四、应用架构（Application Architecture）

### 三类用户界面与主体

| 界面/应用 | 归属 | V1.1 定义的使用方式 |
| --- | --- | --- |
| 客户前台 | VEYFRONT | 诊断介绍、网站输入、受理/进度/失败状态、已审核报告和企业微信/表单咨询 |
| 内部 Operator Console | VRAE | 任务池、证据对照、逐项审阅、报告版本、费用及运营交接 |
| 获准报告访问 | VRAE / VEYFRONT | 对自身获批准的精确版本进行授权查看 |

第一版内部审核台不要求复杂独立 SPA，可用受保护的服务端模板与轻量交互。角色包括 Operator、Reviewer、Owner 和获授权的外部客户，各自按任务/版本/租户受限。

### 两种入口

1. **内部精准开发**：企业来源合法性核查 → 候选登记 → L0 公开只读核查 → 内部是否开发审核 → 沟通草稿 → 人工审批首次商务触达 → 客户回应并同意进一步讨论 → L1/L2 → VEYFRONT 咨询/报价。
2. **客户自愿申请**：VEYFRONT Rebuild 页面与授权说明 → 输入网站 → VRAE 持久受理 → 最小进度状态 → 人工审阅 → 获准有限报告 → 企业微信/表单主动沟通。是否开放匿名免费初查属于单独商业决策。

### 工作台与客户 L1 报告

- 任务池：待办、阻断、运行、补证据、待审核、已批准、已分享和费用。
- 证据比对：页面 URL、观察时间、截图、规则定位。
- 审阅：对 Observation / Hypothesis / Recommendation 拒绝、改写、批准；原始 Evidence 不可编辑，审批绑定具体报告版本。
- 商务交接：仅用获批准版本与 VEYFRONT 不透明引用关联。
- L1 一页内容：企业公开网址、日期、覆盖页范围、最小采购商旅程；最多三个「证据事实 → 可能影响（假设）→ 建议动作 → 验证方法」；标准 Rebuild/定制范围区分；15 分钟讨论、企业微信与 Rebuild 咨询；版权、使用范围和未检查部分说明。

### V1.1 候选 API 与跨系统合同

| 候选端点 | 责任 |
| --- | --- |
| POST /v1/audit-requests | 持久受理申请，202 不代表诊断完成 |
| GET /v1/audits/{id} | 查询任务最小状态 |
| GET /v1/audits/{id}/report | 精确授权版本读取 |
| POST /v1/audits/{id}/review-decisions | 按版本/内容哈希审阅 |
| POST /v1/reports/{id}/share-grants | Owner 对获批准版本发放授权 |
| POST /v1/audits/{id}/sales-handoffs | 受权商务交接引用 |
| GET /v1/health | 内部健康状态 |

跨系统：Audit API V1（VEYFRONT ↔ VRAE）、Growth Event V1（往 Vey2GE，首期仅合同）、RebuildBrief V1（经客户授权交 L2M）、Evidence handoff（授权证据副本到 L2M）。各系统不共享数据库。
