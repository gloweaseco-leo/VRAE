## Candidate topology, not provisioning

Choose a vendor-neutral private Linux container host for the **next Owner-reviewed staging design**: API, canonical Worker, one private PG16 and private encrypted evidence/review storage in the same Owner-selected region. Browser/CRM remains VF's responsibility; an eventual VF BFF sends authenticated asynchronous requests and polls read-only status. It never starts a Worker directly. This repository's present adapter remains callable and private; no ingress exists in the drill.

| Option | Assessment / decision |
| --- | --- |
| Private container host + private persistent disk, single PG | Chosen candidate for predictable original process/UID/loopback behavior and explicit network controls. Single-host loss remains a failure domain; no HA claim. Provider, region, legal location, operator and recovery target pending Owner. |
| Independent managed PG + object storage | Potential later separation/backups, but current original loopback connection and bytes/SQLite authority require migration design, TLS/private routing, retained version pins, credential rotation and actual restore evidence. No service created. |
| Vercel front/BFF with external VRAE runtime | Candidate boundary only after C2 auth/G0 freeze. Current [Vercel Services](https://vercel.com/docs/services) supports grouping frontends/backends; that capability alone does not validate our PG durability, controlled identity or deny-egress worker requirements. No Vercel project/deployment/domain is created. |

Local configured limits are PG 1 CPU/512MiB and supervisor+children 1 CPU/768MiB, not measured peak use or production minimums. Each public result records **MEASURED** wall time, PG size, dump size and original activity wall time for one synthetic task. CPU peak, RAM peak, concurrent throughput and p95 are **UNKNOWN**. Network: local PG is `--network none`, no published ports. Runtime shares only its loopback namespace; real worker UID probes fail `ENETUNREACH` before packet egress, route/interface checks are recorded. This follows [Docker none network](https://docs.docker.com/engine/network/drivers/none/). Local API/PG are intentionally reachable inside that namespace; this is not kernel per-UID isolation. Future staging ingress, DNS/TLS, reverse proxy and separate authenticated backend networks require a reviewed change to the existing fixed loopback boundary. Egress remains DENY; no public/model route is a default.

Secrets: original per-role 0600 files under 0700 UID-owned dirs, no Docker socket/host credentials/issuer key in worker. Root is trusted disposable bootstrap. Candidate service secrets must be fetched under dedicated workload identity, rotated independently with current-key invalidation, audited without raw tokens, and recoverable through approved escrow. Current controlled keys reset on process restart; do not offer permanent customer identity or extend P40/report TTL.

Storage/retention: protect raw evidence, report versions, creation stamps, review ledger, authority/revocation records and backup manifests separately from public metadata. Retention/deletion/legal hold durations and object-store region are Owner decisions; no public bucket or share link. PG dump gives a DB snapshot; [PostgreSQL docs](https://www.postgresql.org/docs/16/backup-dump.html) distinguishes single-DB dumps from cluster-global roles. Current same-cluster restore retains roles and independent files; full DR needs encrypted off-host backup, globals/secrets, source hashes, PG+SQLite consistency strategy and restore drills on a fresh host.

Logs use task IDs/stages/codes/hashes only; raw fixture/credential/debug logs stay private. No external monitoring account created. Admission should stop before draining jobs; then stop workers without changing leases, back up stopped writers, preserve forensic owned resources on unresolved cleanup error, and require a verified restore before restart.
