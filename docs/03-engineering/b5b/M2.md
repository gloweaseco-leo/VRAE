## Component and integration boundary

`b5b_http.Application(..., generated=GeneratedConsole(...))` mounts generated
routes in the **existing** signed B5B HTTP server. The optional private loader is
`b5b_profile.load(..., generated_profile=<private Reviewer-only JSON path>)`.
There is no new executable product HTTP server. Without provisioning, the old
explicit missing-port workspace remains; no synthetic success is substituted.

Private provisioning shape (`b5b_m2_profile.provision`/`load`):

```text
version = M2_SYNTHETIC_REVIEWER_1
anchor = {issuer, audience, jwks: public Ed25519 JWKS only, expires}
assignments = [M1 JobAssignment fields: issuer, subject, db_role, tenant,
               job_id, expires, active]
reviewers = {<allowed Reviewer role>: {password}}
tasks = {404|200: {tenant, job_id}}
task_endpoint = {bearer: private HTTP API bearer, tenant_id,
                 source_refs: [accepted-404, accepted-200]}
task_journal = <private durable routing SQLite path>
```

Only low-role Reviewer passwords/public keys and the separately provisioned
HTTP service bearer enter SSR. No APP/Worker DB config,
signing key, arbitrary DSN/URL or uploaded report/source bytes. Fixed loopback PG
5432, original database, 2-second statement/lock timeouts; no role change.
The launcher owns private file permissions and trusted provisioning. Changing
the loaded profile invalidates existing generated sessions, including the final
pre-COMMIT check; it does not silently update authority. Restart requires fresh
issuer/challenge provisioning. DB assignments still independently authorize.

Routes under `/b5a/m2/`:

- `/`: choose a current assigned actual generated task; `/challenge` POST obtains
  server-held nonce/CSRF. `/session` POST alone accepts a signed bearer header.
  Original `SignedGeneratedReader.read` validates it and replays native bytes.
  No raw bearer is stored or rendered. Opaque HttpOnly/SameSite=Strict cookies
  use only this path. Session lifetime is bounded by token, anchor, assignment
  and existing 120-second maximum, never extended by navigation.
- `/tasks`: after a current assigned signed login, choose the authorized 404 or
  200 synthetic source and see this Reviewer's own submission history.
  `/create` POST uses one-use CSRF and the accepted `TaskClient.create`; only a
  real APP202 yields the persisted request/run/job/event handle. It rechecks the
  current parent assignment around admission and never passes APP DB config.
- `/task/{opaque_ticket}` queries `TaskClient.status` and validates its actual
  request/run/job/source correlation. PENDING has no report read control. DONE
  only enables a new signed challenge. A server-side `JobAssignment` routing
  binding derives issuer/subject/role/tenant/expiry from the verified Reviewer;
  it NEVER writes or grants a DB assignment. `TaskClient.read` calls the original
  signed M1 reader; Worker COMMIT's current DB assignment still decides access.
  Report version/hash comes only from that signed result, never status metadata.
- `/report`: fresh original M1 locked read plus native `replay` on every request.
  Exact request/run/job/report/version and separate whole-file/content hashes,
  original Guard/Evidence, explicit editorial omissions, at most three issues.
  The 200 summary does not invent CTA claims, success, or site health.
- `/review` POST: single-use, path/session-bound CSRF; exact generated version
  and whole-report SHA; exact issue IDs; internal approve/reject/revise and
  bounded revision notes. Receipts are returned only after actual COMMIT.
- `/receipt/{command_id}`: current assignment/version-bound durable readback.
  `/report` lists the latest 20 authorized receipts, including after restart.
- `/export[/{command_id}]`: separate escaped Chinese A4 projection with an
  explicit synthetic/internal/no-external-delivery watermark. Original M1 HTML
  remains byte-exact. Long revision notes are visibly summarized on paper; full
  notes remain in the durable receipt. Printing to PDF uses the real browser.

## New internal ledger, not report or human-approval authority

Install only `db/b5b_m2/001_internal_review.sql`, after the accepted M1 migration.
New schema/table/functions only. Runtime has function EXECUTE and zero table
privileges. Receipts are immutable, tenant-RLS protected, reviewer-bound,
version/hash-bound and idempotent by command UUID. SQL calls the original
`m1_read_assigned` and retains its origin/assignment/tenant locks through COMMIT.
A deferred trigger rejects a receipt if its signed-session deadline has elapsed
at actual COMMIT. The SSR also checks anchor/assignment/session freshness before
COMMIT. No receipt changes `NOT_APPROVED`, semantic approval, a report byte,
ShareGrant, external recipient, delivery, or real human approval.

## Accepted TaskClient integration and restart recovery

Task submission/status now directly reuse Owner-merged PR105's `TaskClient`,
`AppEndpoint` and `TaskHandle`; no sibling Draft or second HTTP client/producer.
Source aliases are fixed to the private endpoint allowlist. Tenant must match the
current signed Reviewer. Handles, source, owner (issuer/subject/DB role/tenant)
and server-generated idempotency keys are saved in a private routing journal;
it stores no report bytes, API bearer, signing key, or authorization grant.
Lost APP responses are recovered using the SAME persisted key. An unknown
submission cannot be replaced with a guessed handle or a fresh duplicate key.
After a real PG and SSR process restart the same routing file lets a freshly
authenticated Reviewer find their task, query the real APP, re-sign its result,
read its original immutable receipt, and export the same version/hash to A4.
Signing keys remain outside SSR and rotate for a fresh test process; old cookies
fail after restart. Assignment checks are per exact current binding, so adding a
new routing binding cannot silently extend, revoke, or alter another session.

The controlled launcher supplies at least one current genuinely generated,
assigned task for the initial existing job-scoped signed identity check. This is
an actual M1 result, never a legacy sealed fixture. Browser acceptance then
submits a DIFFERENT fresh task for each source and follows only its new result.
The existing `integration.b5b.http_server` also accepts `--generated-profile`;
it mounts these routes on the same server and announces `/b5a/m2/` as entry.
