# 新诊断无需一次性 Preview 邀请

Owner 要求取消一次性邀请和短会话给正常诊断带来的客户阻断。
本修复只处理已认证 VF 后台建立诊断会话这一断点，复用原PG会话、签名授权、队列、Worker、Qwen、Guard和结果端口。
不改VF仓库，不增加用户登录、DNS核验、独立AI同意或人工签发步骤。

## 已确认的事故原因

2026-11-20 08:17:56 UTC只读检查：原Preview角色和证书均有效至次日05:16:57 UTC，
已私有交接的一次性邀请 `used=true`，唯一旧会话于当天06:08:29 UTC到期，有效会话数为0。
原任务数/工件数/模型账本没有新增。详细脱敏状态见 `incident-state.json`。
部署核验曾只覆盖服务、证书和新结果契约，漏掉已消费邀请与会话生命周期。

没有把旧邀请改为可反复使用，没有恢复旧会话或放宽旧任务读取条件。

## VF 最小接入

VF后台在**开始一次新诊断、首次提交之前**调用：

```http
POST /v1/diagnosis-sessions
Accept: <沿用现有VRAE media type>
Content-Type: <沿用现有VRAE media type>
Authorization: Bearer <原服务端凭据>

{}
```

连接继续使用原mTLS客户端证书及服务端源码SHA校验。不传邀请、租户、用户标识或网站。
成功返回200、`{"created":true}`，以及与原入口相同的 `Set-Cookie` 和 `X-CSRF-Token` 响应头。
Cookie仍为 `__Host-vrae-targets`，带Secure/HttpOnly/SameSite=Strict及有效期；原Cookie/CSRF传递方式可复用。

VF随后使用该访客的Cookie/CSRF调用原 `POST /v1/diagnoses`：网址与
`VRAE-AUTO-DIAGNOSIS-1` 一次授权声明不变，轮询原 `GET /v1/audits/{audit_ref}/diagnosis`。
不再读取或消费 `VRAE_PREVIEW_INVITATION` 来开始新诊断。

会话只保存在该访客的上下文，不能作为所有访客共享的进程全局值。
Vercel冷启动、重新发布和用户闲置后开始新诊断，都可重新调用本入口，不依赖进程内缓存或操作员换邀请。
后台仍使用有期限的服务凭据并正常轮换；凭据维护不是客户操作。

内部会话仍短期有效，过期后新诊断由后台取得新会话。
**新建会话仅用于新的诊断意图。不要在轮询时新建会话，不要把已提交或提交结果不确定的旧请求跨新用户上下文自动重提**，
避免重复采集或计费。旧任务沿用原会话/恢复票据及原当前权限，不会转给新会话。

## 后台控制与实现

- 新SQL函数仅授予独立NOLOGIN组 `target_v1_session_issuer`；原受信初始化器仅向启用网址接入的正常APP绑定授权。
  AI、REVIEW、健康探针及未授权角色不能借此创建会话，原运行角色仍无表读取/写入权限。
- HTTP入口必须通过原Bearer、证书绑定、租户作用域，且仅允许空JSON对象；浏览器不能指定身份。
- 用户标识及兼容上下文由PG随机生成。内部复用原invitation记录结构，其随机token不发放且标记已消费，
  不产生共享邀请或旧任务访问权。
- 原每租户capacity锁串行处理创建，1000个同时有效自动会话为后台资源上限；到期会话不阻止新会话创建。
- 原30分钟Cookie生命周期与服务身份截止期保持后台约束；新诊断不再因共享邀请耗尽而永久无法建立会话。
- 建会话不创建网站计划、任务或模型预留。实际诊断仍必须有用户一次授权、受限同源采集、robots/SSRF控制及原费用许可。

Migration007在原initialize中追加，历史记录不改写。
初始化不会启用已关闭的网址接入，也不会激活已撤销角色或修改其epoch。
