# ADR-0001｜独立 VRAE 仓库与模块化单体架构

- 状态：ACCEPTED — 2026-11-10 的用户架构认可
- 取代：VEYFRONT Draft PR #26 中“VRAE 源码长期归属 VEYFRONT”的原始提议
- 本 ADR 是架构选择，不是运行时交付记录

## 背景

VEYFRONT 目前是 Next.js 品牌、咨询与销售入口；Legacy2Modern 提供仍在验证中的网页生成能力和部分可用的受控采集代码；Vey2GE 是跨行业增长经营产品，但其生产集成仍需独立验收。

若将 VRAE 作为 VEYFRONT 组件，会把不可信网页抓取、Chromium、队列、证据和 AI 成本与官网的部署和安全边界绑定。直接依赖 L2M/Vey2GE API 则引入尚未具备的生产 SLA 和跨系统故障链。

## 决策

1. 独立仓库：gloweaseco-leo/VRAE；
2. Python 优先模块化单体；逻辑模块分离、发布版本一致；
3. API 与隔离 Worker 分进程、分最小权限；
4. 独立 PostgreSQL 与私有对象存储，不共享 Vey2GE/VEYFRONT 表；
5. VEYFRONT 通过 VRAE 有版本的 API 调用；Vey2GE 经事件/接口适配；L2M 经客户授权接收 RebuildBrief；
6. L2M 的安全采集仅经许可、固定提交、测试后做最小必要提取；不复制全部项目。

## 拒绝方案

- 在 VEYFRONT 仓库直接增加采集 Worker：短期便利但耦合部署、安全和进度。
- 在 L2M 增加审计 API：诊断成为生成引擎的附属功能，且依赖未验收的生成系统。
- 初期即建设微服务、多 Agent、通用 SaaS：运维成本大于当前销售试验需要。
- 两项目直接共享数据库：数据所有权、迁移、租户隔离和权限职责不清晰。

## 后果

多维护一个仓库和 API 部署，但使 VRAE 可独立开发、复用、验收、部署与暂停。合同和身份映射成本应通过清晰的 API/OpenAPI、事件版本和契约测试控制。不得因为“仓库已建立”就宣布系统可用。

## 复审触发

VRAE 单独商业化、多行业复用、诊断任务显著增加、数据地区与安全要求变化；若共享底层采集能力验证成熟，可考虑再提炼成双方引用的版本化库。
